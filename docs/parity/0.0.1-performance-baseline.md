# 0.0.1 performance baseline

Recorded on 2026-08-09 from commit `b76dc81` plus the parity harness in issue #231.

## Conditions

| Property | Value |
| --- | --- |
| Deployment | Electron production build, E2E mode, 1200 × 800 window |
| Operating system | Fedora Linux, kernel 7.1.6-201.fc44.x86_64, x86-64 |
| Processor | AMD Ryzen 7 9800X3D, 8 cores / 16 threads |
| Memory | 60 GiB |
| Git | 2.55.0 |
| Node used for recording | 22.23.1 |
| Repository | 10,000 linear commits, 202 tracked files, one 100-line untracked file for working-copy interactions |
| Cache state | New application profile for every run; OS filesystem cache warm because the repository fixture is created immediately before launch/open measurements |
| Concurrency | One Playwright worker; no other parity test running |

The project declares Node `^24.15.0`; this workstation recording used Node 22.23.1 and emitted the
engine warning. Future comparisons must record their Node version and should use the declared engine.

## Method

Run a production build, then run the opt-in baseline test:

```bash
pnpm build
REBASE_PERFORMANCE=1 pnpm playwright test e2e/performance.spec.ts \
  --grep "records the 0.0.1" --workers=1
```

Startup begins immediately before `electron.launch` and ends when the first rendered root surface is
visible. Repository open begins before the isolated store is pointed at the repository and ends when
status plus the first 2,000-entry history page are visible. History-page time is the interval from the
2,000-entry page to the 4,000-entry page. External refresh begins immediately before the external
filesystem write and ends at the DOM mutation that makes its status row visible. Stage, unstage, and
diff timings begin before the visible click and end when the resulting row or diff line is visible.

The test attaches `performance-results.json` with exact floating-point results. The table rounds the
recorded run to the nearest millisecond.

## Results

| Interaction | Ceiling | Baseline | Headroom |
| --- | ---: | ---: | ---: |
| Startup to usable surface | 2,000 ms | 892 ms | 1,108 ms |
| Repository open to status and history | 1,000 ms | 181 ms | 819 ms |
| External edit to visible status refresh | 500 ms | 430 ms | 70 ms |
| Stage click to visible index state | 150 ms | 61 ms | 89 ms |
| Unstage click to visible worktree state | 150 ms | 145 ms | 5 ms |
| Diff open to rendered line | 200 ms | 38 ms | 162 ms |
| Next 2,000-entry history page | 250 ms | 38 ms | 212 ms |

The always-on external-refresh E2E check uses a small real repository and the same DOM-mutation
timestamp method. It was repeated three consecutive times during harness validation and passed the
500 ms ceiling each time. The full representative-repository measurement remains opt-in because its
absolute values are intentionally machine-sensitive; release comparisons must use the same machine,
repository shape, worker count, and cache method.
